2026-10-10 confirmed 7-field support

Both confirmed 7-field and original 11-field STATUS are now automatically
validated/decoded without sending FULL or requiring a firmware update. A run
locks its format after the first selected frame; switching formats during that
run faults instead of mixing button/stop interpretations. Raw ADC/target/PWM/ESTOP
fields missing from compact STATUS are None/unavailable, never synthetic zeros.
The first base RPM is ignored locally, then new 5-RPM increases/decreases infer
UP/DOWN as before. Actual left/right RPM fields drive the existing odometry.

Compact STATUS has no wheel-target report or ESTOP flag. Terminal instant-stop
therefore requires a complete HOST zero-RPM write followed by three distinct
zero measured-RPM observations at least 50ms apart. Coasting RPM resets the
confirmation count; batched duplicate frames cannot satisfy it. This is logged
as legacy_stop_standstill_observed, NOT an MCU command ACK. UP in/before the
confirming sample is consumed; a later UP resumes the saved speed/curve.
Original 11-field mode retains its zero-target feedback barrier. The compact
mode cannot independently observe physical ESTOP state or firmware fault cause.

Deployment prerequisites

The default is now Jetson-only: MCU_PROTOCOL=legacy uses the already-deployed
$CMD/$STATUS ASCII firmware. No STM32CubeIDE project, ST-LINK, build or firmware
upload is required. The optional previously implemented $FULL/$CTRL extension
is NOT sent/required in default mode. An actual robot test has not been performed
in the development PC.

The previous robot run used MCU_OPEN_LOOP=1 because STM32 status was not reaching
Jetson. Full run requires receiving the firmware's EXISTING $STATUS messages to
read UP/DOWN changes and actual wheel RPM. Updating firmware is unnecessary, but
software cannot infer button presses from an absent return signal. No live
STATUS means zero motion and an automatic diagnostic bundle, not open-loop mode.

1. Copy the entire project to Jetson, keeping the directory structure.
2. Keep the existing STM32 firmware. Do NOT replace/upload main.c or headers for
   normal full-run deployment. The STM32 extension in this repository is optional
   only for explicitly selected MCU_PROTOCOL=ctrl, which is not the default.
3. Keep the working command connection (Jetson TX -> STM32 USART1 RX). Verify
   the existing status output (STM32 USART3 TX -> Jetson UART RX), with common
   GND. /dev/ttyTHS1 and /dev/ttyTHS2 are only default device names, not verified
   connector/pin mappings. Set MCU_STATUS_DEVICE in config/full_run.env to the
   actual receiving port. It may equal MCU_DEVICE if its RX receives USART3 TX;
   both directions can use one Jetson UART. The MCU's TX/RX and Jetson's RX/TX
   pins must be identified on the actual board before changing a physical wire.
   Default command-RX discovery also covers an existing STATUS return wire
   on MCU_DEVICE, without changing that wiring or the configured device names.
4. This robot's side HC-SR04 sensors connect to STM32. Keep that wiring and the
   existing firmware; left_us_cm/right_us_cm arrive through compact STATUS.
   Default SIDE_SENSOR_SOURCE=mcu needs no Jetson GPIO wiring/library. For a
   DIFFERENT gpio-wired robot only: left BOARD TRIG=33 ECHO=31, right TRIG=7
   ECHO=15, with appropriate voltage shifting and carrier pinmux configuration.
5. Run: sudo bash scripts/setup_full_run.sh
   This prepares software only and does not flash or start movement.
   It attempts independent installation/check stages even after another stage
   fails. It returns nonzero if anything failed or was blocked; do not treat
   reaching the final line as successful installation. See "Setup diagnostics".
6. Run: sudo bash scripts/start_full_run.sh --check
   This checks files/imports/device access/configuration only.
7. Run: sudo bash scripts/start_full_run.sh --preflight-only
   This starts the actual devices and requires fresh YOLO, LiDAR, $STATUS and both
   side-sensor samples from the selected source, enforcing zero RPM even if UP is pressed. Success
   does not prove that NO_ECHO represents open space rather than a disconnected
   ultrasonic sensor: both cause no rising edge. Point a known object at each
   sensor and inspect VALID readings in the log to confirm physical operation.
8. Run: sudo bash scripts/start_full_run.sh
   Wait for READY in logs/full_run/latest/controller.log, then press UP.

Manual stop/restart and automatic boot

Foreground: Ctrl+C sends stop/brake commands and cleans up owned processes.
From another terminal: sudo bash scripts/start_full_run.sh --stop
Restart: sudo bash scripts/start_full_run.sh
Stop validates PID start time and actual script path to avoid signalling reused
PIDs. Starting a second full run, or taking a serial port/container from another
launcher, is refused. The controller checks its launcher's PID/start time and
stops if that launcher vanishes. A lost controller is also stopped by the STM32
command watchdog (current main.c: 800ms). SIGKILL prevents shell cleanup; use
systemctl stop for a service or normal Ctrl+C/--stop for manual processes.
An entirely new process discards the old path, resets
requested speed to zero via a fresh session and requires a new UP press.
In legacy mode that reset is LOCAL to Jetson: the old MCU base RPM is not reset.
The initial base value is logged and ignored; only later changes are button
evidence after READY. Startup presses are consumed, not queued for later motion.
The first incoming STATUS never starts a new process moving. An old ESTOP left
by previous shutdown is allowed to clear under zero commands before READY;
it is not misclassified as a new stop that deadlocks startup.

Immediate user stop WITHOUT exiting the process:
  sudo bash scripts/start_full_run.sh --instant-stop
The launcher stays alive, drops to zero without a ramp on the next control
cycle, and keeps the avoidance plan. A new observable UP resumes saved speed.
Wait for legacy_stop_acknowledged (11-field mode) or legacy_stop_standstill_observed
(7-field mode) in controller.log before UP. Confirmation is not hard real-time.
The STATUS establishing the zero-target/standstill barrier sets a new baseline;
an UP in/before that acknowledgement is consumed so a queued press cannot undo
the stop. A later UP resumes. The timing is not a hard real-time guarantee.
The command sends an atomic request addressed to that launcher's PID/start time,
not a second serial writer. Missing/stale/reused/unrelated PIDs are refused.
This is a software stop, not a safety-rated physical emergency-stop circuit.

To enable at power-on:
  sudo systemctl disable --now amr-core.service   # only if previously installed
  sudo bash scripts/install_full_run_service.sh
  sudo systemctl start amr-full-run.service

The installer substitutes this checkout's absolute path into the supplied unit,
validates it and enables it for the next boot. It refuses an enabled/active old
amr-core.service, which would compete for the same devices. It does not start
the robot during installation. The unit runs as root to access UART/GPIO/Docker.
An automatic process restart still resets to READY/zero and needs UP.

Service commands:
  sudo systemctl stop amr-full-run.service
  sudo systemctl start amr-full-run.service
  sudo systemctl status amr-full-run.service
  sudo journalctl -u amr-full-run.service -b --no-pager

After stopping the service, the same foreground command is usable manually.
If systemd reached its restart limit, use systemctl reset-failed before start.

Buttons and stopping

Legacy firmware keeps PA4 UP and PB7 DOWN unchanged. It alters its base value by
5 RPM within 0..65 and reports that value about every 100ms. Jetson infers UP
from an increase and DOWN from a decrease, applying those changes to its own
0/5/10/15/20 selected speed. A DOWN still subtracts 5 at the software speed cap,
even when the firmware's raw base value is higher than 20. Speed zero pauses.
After --instant-stop or an observed legacy ESTOP, the first UP restores selected
speed instead of increasing it. A raw ESTOP still reported prevents departure.

Legacy STATUS does NOT include hold duration or raw button edges. Long DOWN
instant-stop is therefore REMOVED in default mode; use --instant-stop instead.
Press/release buttons distinctly, with at least ~0.2s between operations: an UP
and DOWN both between two STATUS messages can cancel and be unobservable. At
the old firmware's raw 65 RPM limit, UP cannot change the reported value. To
restart there, press DOWN once and then UP. This restriction is printed/logged;
it cannot be eliminated by decoding existing STATUS. Multiple rapid changes or
MCU reboot cannot be reconstructed exactly from a single base value.

An existing physical instant-stop is only observed if it changes legacy ESTOP.
No new hardware stop GPIO or hold behaviour is assumed. Firmware/hardware fault
cause is absent in STATUS; missing communications, bad GPIO and no wheel progress
still produce latched FAULT_STOP. An observed ESTOP with healthy communications
is a user pause, consistent with the requested UP-resumable instant-stop policy.

Speeds: 0/5/10/15/20 RPM, per-wheel limit 20; entry cap 12, passing cap 16,
return cap 14, always also limited by user RPM. Normal speed changes ramp in
the Jetson. The old firmware's buttons alone do NOT immediately clamp received
wheel commands: Jetson applies speed changes after receipt of the next STATUS
(nominal 100ms + next 20ms control cycle, not a hard real-time bound). Its original
command watchdog remains active independently. Do not assume the optional new
firmware's motor gate exists on an unchanged MCU.
Wheel commands are scaled together to preserve turn curvature.
Front stop/resume thresholds are measured from the front bumper across the
full 90cm body width plus lateral margin, using calibrated LiDAR points; the
raw radial front range is also retained in snapshots for diagnosis.

User zero/instant stop and temporary blocked-space stops preserve phase, exact
curve/follower progress, frozen obstacle, baseline, seen/tail state and rear
distance. Reported-RPM pose estimation continues; phase timers and tail counters pause. A
fresh UP is required after hazards clear. A blocked UP is consumed and never
causes a later automatic departure. Persistent sensor/communication/firmware
faults latch FAULT_STOP and require stopping/restarting after repair.

Avoidance

DRIVE -> STOPPING (0.3s) -> ENTRY curve -> BASELINE (stationary samples) -> PASS
-> REAR_CLEARANCE -> RETURN curve -> DRIVE, repeated continuously.

YOLO confidence >=0.45, three consecutive frames, matched LiDAR cluster and
drive-corridor intersection, forward distance <=2m trigger normal avoidance.
The object and curve are frozen so losing the detection does not lose the plan.
The tracked point is allowed to move along the frozen object's lateral strip
for a long face, even after a YOLO ID change. A new object in the passing lane
is still checked independently, and the front/body clearance guard stays active.
Choose the opposite side from the object's bearing, subject to lateral and
diagonal clearance. No safe side produces a recoverable pause. Do not force
the old minimum 0.65m entry if it would erase the chassis-front clearance;
insufficient entry room pauses instead. Another object on the saved path pauses
without overwriting it. UP can resume once that object no longer blocks it.

Passing uses the sensor facing the obstacle (left bypass -> right sensor).
Save five initial samples, with valid median or NO_ECHO baseline. A close
echo in (0.30,0.70]m plus matching side LiDAR, or two consecutive close echoes,
arms side-object tracking. Baseline samples can already arm it if alignment
ended alongside the object. A thin pole can arm with one corroborated echo.

After arming, require five new far samples (>=0.85m or NO_ECHO) plus side LiDAR
clearance >=0.85m, after at least 3cm measured motion, to confirm the tail.
A distant numeric baseline also requires return to at least baseline minus
10cm. A close baseline may be the obstacle itself, so returning to that same
close distance never confirms a tail. Raw distance decreases on approach and
increases on departure; the old displayed 0.0 is not treated as real distance.

Confirmed tail -> extra forward x displacement 0.425+0.15=0.575m for centre
sensors -> return to original y=0 path. Default legacy estimates this displacement
from REPORTED wheel RPM, wheel size and host receive/control time, NOT commanded
speed. It has no cumulative counts/MCU timestamps and is less accurate; quantized
100ms telemetry and slip require checking clearance on the actual robot. Legacy
RPM values can freeze while its ESTOP flag is set, so those values are suppressed
instead of creating fictitious motion. Optional ctrl mode uses cumulative
encoder counts when present. Rear clearance uses forward x displacement, not
absolute distance travelled, so reverse motion cannot complete it.
A new close face cancels tail clearance
and returns to PASS. Three metres without ever seeing the object faults with
a sensor-source/wiring/orientation diagnosis; ten metres without a tail pauses.
Timers do not run while paused. In optional Jetson GPIO mode, the inside sensor
gets three samples for each outside sample, with 60ms between triggers. Default
STM32 mode consumes both reported values at each STATUS reception; the deployed
firmware controls sensor sampling. Both remain monitored for reception staleness.

Setup diagnostics

The same sudo bash scripts/setup_full_run.sh command records each attempt in
logs/full_run_setup/<UTC time>-<unique suffix>/:
  launcher.log: all stages' stdout/stderr, UTC start/end and final summary
  <step>.log: individual apt/ROS/LiDAR/model/Docker/GPIO/check output, failing
              worker command, source line and exit code
  stages.tsv / summary.txt: OK, SKIP (already usable), FAILED and BLOCKED results
  system_before.log / system_after.log: OS/L4T/Python/Docker/package versions
  source/: the installer, model/Docker helpers, Dockerfile and config used
  *_reuse_probe.log: failed existing-workspace checks before deciding to rebuild

ROS bridge, LiDAR source/build, model download, Docker image, Jetson.GPIO and
configuration checks are separate steps. A failed apt index update does not
prevent trying installation from existing indices. A Docker failure does not
hide ROS/GPIO/configuration problems. Read-only final checks run even after
failed installations and report additional missing resources. Multiple Python
imports are checked individually so one bad module does not hide another.

An unsupported platform/non-root invocation blocks system changes, but still
records the environment and runs possible read-only checks. A failed build-user
context blocks user-owned builds; a failed LiDAR clone blocks its build; a failed
Docker daemon check blocks its runtime/image build. These are explicitly BLOCKED,
not success. This is not blind continuation of commands with invalid inputs.
The failing step itself stops at its first command failure, then the runner
attempts the next independent step. Impossible downstream work cannot reveal
all of its potential errors until its prerequisites are repaired.

At the end of a failed/incomplete attempt, an automatic archive containing ALL
attempted stages is saved as logs/full_run_setup/<time>-<suffix>-debug.tar.gz.
The combined log writer is flushed before compression. If Python packaging is
unavailable, tar is used as a fallback. Original logs and previous attempts are
preserved. Disk/permission errors preventing log creation/writes, or Ctrl+C/
SIGTERM, can prevent completing every step; the attempt is marked incomplete.
After repairs rerun the same setup command; usable packages/workspaces/model/
image/GPIO imports are reused. No services/motors are started by this setup.
The original setup_yolo_lidar_path_avoidance.sh keeps its fail-fast behaviour.

Record format and debugging

Each invocation creates logs/full_run/<UTC time>-<unique suffix>/.
latest links to the last successfully owned live run (checks do not replace it).
  launcher.log: dependency checks, shell line/command failures, child exit codes
  controller.log: state/phase changes, refusal reasons and Python stack traces
  events.jsonl*: UTC + monotonic timestamp, raw scans/YOLO/UART/echo pulses,
                 wheel TX and heartbeat gaps, 10Hz pose/status/phase snapshots,
                 frozen geometry, path control points and counter progress
                 In legacy: raw STATUS, inferred button deltas/local selected
                 speed, host clock/pose-estimation source and unobservable limits.
  lidar.log / bridge.log / yolo.log: each child process's stdout/stderr
  shutdown.log: independent fallback stop command result
  config.json / system.txt / source.sha256 / source.tar.gz: exact configuration,
                 board/package/device metadata and source snapshot for this run
                 STM32 source files in the archive are OPTIONAL repository code,
                 not proof of what firmware bytes run on an unchanged robot.

JSONL uses 16MiB files with 24 backups (~400MiB maximum per invocation).
Old run directories are preserved, not deleted automatically. GPIO NO_ECHO,
stuck-high, too-short pulse and missing-edge timeouts are logged distinctly.
There is no camera-video recording or claim that software can determine wiring
faults from no echo alone. Rotation/write failures stop the controller.

Debug bundles are now automatic when running start_full_run.sh:
  - Startup/dependency/configuration errors: archive the failed attempt's log.
  - FAULT_STOP (even when the controller remains alive): archive in a separate
    process after zero RPM is sent, without blocking the motor heartbeat.
  - Sensor/controller process crashes, exceptions or forced shutdown: archive
    after motors and owned processes have stopped.
Normal READY, user pause/instant stop, blocked-space pause, Ctrl+C and normal
--stop do not trigger an archive unless a fault already occurred in that run.
There is one automatic <UTC time>-<suffix>-debug.tar.gz per failed invocation
in logs/full_run/. The path is printed as [BUNDLE] Saved in launcher.log.
auto_bundle.request.json preserves the first reason; auto_bundle.status.json
records successful completion. While running, the first-fault archive is not
refreshed. After motors and owned processes stop, the same archive is finalized
once with final/cleanup logs AND the exact original archive nested inside as
first_fault-debug.tar.gz. Send only the final outer *-debug.tar.gz; rotated logs
cannot erase that nested first-fault evidence.
Files are published atomically; incomplete compression is never presented as
a completed archive. bundle_metadata.json records capture times and the exact
prefix size captured from each live log. Original logs are never removed.
If compression fails (for example, full disk), inspect bundle.log; shutdown
retries a failed background capture. Failed finalization leaves the original
archive intact. Repeated finalization does not wrap the archive repeatedly.
The service allows 120 seconds for shutdown/compression; motors stop first.

Additional diagnostic coverage

Independent read-only startup file/device/configuration/import/ROS/Docker checks
are attempted before deciding whether robot processes may start. imports.json
records all import results/tracebacks and installed ROS bridge source hashes;
setup rebuilds an outdated installed bridge rather than reusing old imports.
environment-start.json is collected before checks; the separate bundler adds
environment-fault.json/environment-shutdown.json, never in the heartbeat loop.
These contain OS/board/package versions, allowlisted settings, UART paths/access/
owners, memory/load/disk/USB, service state, Git revision/branch/dirty paths and
bounded recent kernel/service journals. Each inventory command has a 2-second
timeout. No private full_run.env, full process environment, Git credentials/
remotes or camera images are collected. Review journal output before publishing.

runtime_health adds camera/LiDAR received/valid/invalid counts, ROS publisher QoS,
STM32 side raw-cm/VALID/NO_ECHO/FAULT counts (or optional GPIO trigger/edge counts
and worker liveness), plus maximum control heartbeat gap/work time.
startup_step identifies the failing initialization
operation. GPIO setup/callback/measurement/cleanup and UART exceptions include
full tracebacks; UART errors include the last attempted command. Cleanup failures
return failure rather than successful preflight and request diagnostics. Service
registration also has a full_run_setup/ attempt log and failure archive.

Snapshots add UP/resume barriers, saved curves/frozen targets, baseline/near/
clearance sample progress, required/measured rear travel and nearest corridor
returns, including points inside the configured body. These are diagnostics:
body returns are not masked, safety thresholds are not relaxed and sensor faults
are not bypassed. Camera/bridge logs add startup phases, inference timing and
frame/UDP/publish/error counts. Each Python bundle includes diagnostic_summary.json
with streamed retained-record counts, latest status/snapshot, recent errors,
sensor status distributions and all failed/blocked installation stages.
Corrupt event records do not prevent preserving raw logs. Physical sensor/wire
silence may remain ambiguous. Power loss/SIGKILL/full disk can prevent final
capture; no claim of diagnosing every physical fault from software is made.

Summary: python3 scripts/full_run_diagnostics.py
Optional manual fresh snapshot: sudo python3 scripts/full_run_diagnostics.py --bundle
Send the automatically saved *-debug.tar.gz file for diagnosis, including all components.
For an early launcher failure (before latest changes), supply its printed log
directory as the diagnostics argument. No complete environment dump is collected,
but command output may include local paths, hostnames, URLs or credentials passed
to commands. Inspect diagnostics before committing to a shared/public repository.

Sharing diagnostics through Git

.gitignore allows raw files AND *-debug.tar.gz in logs/full_run/ and
logs/full_run_setup/. Other log folders, the local latest symlink, incomplete
*.part archives and private config/full_run.env remain ignored. The scripts do
not stage, commit or push diagnostics automatically.

New sudo/systemd runs keep root as the log owner but assign the checkout's group
to log directories, set group read/traverse and directory setgid, and use umask
027. Finished archives are 0640 (also in the tar fallback). The checkout's normal
user can therefore read/add them without sudo git or repeated recursive chown.
No world-read or group-write permission is added. This applies to NEW attempts;
old root-only log folders may still need the targeted permission recovery already
described in the chat. A root-owned checkout with a root-only group is not a
normal user checkout and must be corrected separately.

Prefer adding ONLY the completed archive printed after [BUNDLE] Saved:
  git add -- "<actual archive path printed by the launcher>"
  git diff --cached --stat
  git commit -m "Add robot failure diagnostics"
  git push origin main

Run Git commands as the checkout's normal user, not with sudo. Review staged
files so unrelated changes/raw logs are not accidentally sent. Raw JSONL logs
can be hundreds of MiB per run; do not add all of logs/ by default. If Git rejects
an oversized archive, report that error and arrange Git LFS or split archives
before retrying; do not silently omit diagnostic content. If push is rejected
because the remote advanced, fetch and reconcile normally; never force-push.
After the teammate pushes, the developer runs git pull --ff-only origin main
and opens the committed archive. Without a completed bundle, the failed run's
specific log folder can also be committed after checking its size/content.

Hardware-free checks on a Linux checkout:
  python3 -m unittest discover -s tests -p 'test_full_run*.py' -v
  cmake -S stm32 -B .runtime/stm32-tests
  cmake --build .runtime/stm32-tests
  ctest --test-dir .runtime/stm32-tests --output-on-failure

These use fake serial/GPIO/ROS and process stubs. They do not issue real robot
commands. Development-PC tests cover the core and adapter plus host C button
logic; Linux process-group tests are supplied but were not executed on that PC
because WSL could not start (Hyper-V feature unavailable).
The old one-shot controller's ideal-wheel test currently has an 8.27cm return
offset against its 8cm expectation after the earlier chassis-size update; it is
not used by start_full_run.sh. The new full-run geometric return tests use the
8cm tolerance and pass. The one-shot launcher's original behavior is preserved.
